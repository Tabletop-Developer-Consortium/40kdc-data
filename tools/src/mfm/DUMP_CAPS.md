# MFM dump — wargear cap mechanisms

Authoritative notes on **how the GW MFM dump (`_private/dump.json`) encodes wargear
limits**, so the ingest (`wargear.ts`) and future readers stop re-discovering this
ad-hoc. Pair with `dump.schema.json` (the full table/field shape, regenerated by
`gen-dump-schema.ts`; the raw user-provided copy lives at `_private/dump.schema.json`).

**The dump IS the GW app's data and is complete.** Every past "the dump doesn't have
it" conclusion was a *probe bug*, not a gap. Two recurring traps:

- `localisations` is a **locale-keyed object** (`localisations.en.name`), NOT a list.
  Read `loc.en?.name` (fall back to the first locale), never `loc[0]`.
- A field can be present-and-typed but **never consumed** by the ingest. A
  silently-dropped field reads as "no cap." Check `dump.schema.json` before
  concluding a field is absent.

## The settled cap rule (structural — no prose parsing)

Verified empirically (jq) against the dump and the GW app. Each `wargear_option_group`
is one "rule" attached to a miniature `M` that the unit composition fields at model
count `C`. The cap of a **swap** (an optional `wargear_option` with `defaultValue == 0`)
is, in precedence order:

1. **A `wargear_limit` ratio** on a mini-scoped `limited_wargear_choice_set` governing
   the granted weapon → `per_n_models` (smallest ratio binds; see mechanism 1 below).
   E.g. WE Jakhals' Icon of Khorne / Mauler chainblade carry `(10,1)`+`(20,2)` = 1 per
   10, so `per_n_models: 10`. WE Chaos Terminators' power fist `(5,3)` = 3 per 5.
2. **Else `wargear_option.inputType`** (mechanism 3, the table the GW app builds from):
   - **`checkbox`** ⇒ a 0/1 toggle → the swap is capped at **one instance unit-wide**
     → `model_constraint: { max_count: 1 }`. This is the "1 X can be replaced with 1 Y"
     shape — WE Goremongers' blood harpoon, the Tzaangor herd-banner/brayhorn icon, the
     single-model Champion swaps. On a 1-model row, "max 1" ≡ "any number up to 1
     model," so the `Any number`+checkbox rows are **not** exceptions — they are
     single-model rows. On multi-model rows `Any number` is **always** a stepper.
   - **`stepper`** ⇒ a 0..N counter → `any_number` (capped by the model count or, when
     present, a `wargear_limit` ratio, which rule 1 already applied).

`max_count` is an existing `model_constraint` field and is honored by
`data/loadout.ts` `optionCap` (`cap = max_count ?? 1`, then `min(cap, max_count)`),
which `weaponBounds` turns into a per-weapon ceiling — **no engine change**. A
multi-branch "one of A/B/C" checkbox swap caps each alternative at 1 independently
(`weaponBounds` sums the per-option cap onto each added id), which matches GW's
independent "1 X → Y" lines.

**Decisive evidence the rule must read `inputType`:** Goremongers' blood harpoon has
**no** `limited_wargear_choice_set`/`wargear_limit` at all — its only cap signal is
`inputType: checkbox`. The ingest derives swaps from `loadout_choice_set` and so
needs the `wargear_option`/`wargear_option_group` join to recover `inputType`.

## The cap mechanisms (the tables involved)

### 1. `limited_wargear_choice_set` + `wargear_limit` — per-weapon squad ratios
A datasheet has N choice-sets; each governs a set of weapons and carries `wargear_limit`
rows of `{modelCount, choiceLimit}` = "`choiceLimit` per `modelCount` models." Smallest
ratio binds; `modelCount: 0` = a flat per-unit cap. **Ingest:** `miniScopedSingleCaps`
(mini-scoped single-weapon sets → per-option `per_n_models`) and `limitedSetBudgets`
(datasheet-wide single + shared + flat → `wargear_budgets`).

### 2. `loadout_choice_set` (+ `loadout_choice` / `loadout_choice_wargear_item`)
The per-model loadout configurations — the cross-product the ingest reads to derive the
swap *options* (which weapons replace which). `.limit` is the per-model choice count
(Devilfish `limit:2` = one model takes 2 seeker missiles). It does **not** carry the
squad cap — that comes from mechanisms 1 and 3.

### 3. `wargear_option_group` / `wargear_option` — **the app's builder + the cap source**
The GW app builds and enforces loadouts from `wargear_option_group` (one per rule;
carries `miniatureId`, `instructionText`, `isStaticWargear`) + its `wargear_option`
rows (`inputType` checkbox/stepper, `defaultValue`, `wargearItemId`). `defaultValue > 0`
rows are the **base loadout** (read by `deriveDefaults`); `defaultValue == 0` rows are
the optional **swaps** whose `inputType` gives the cap per the rule above
(`swapInputTypesByMiniWeapon` in `wargear.ts`). The join keys on `(miniatureId,
weaponId)` over swap rows only, so a weapon that is both a base item (stepper) and a
swap (checkbox) is disambiguated.
